---

## 1. 评审范围

本意见只回答三件事：

1. 草案作为通信协议是否自洽、是否有硬伤。
2. 草案与 CC Desktop 现行群聊模型是否匹配。
3. 若要服务本项目，应保留什么、删除什么、先做什么。

不评审文笔与 RFC 罗列完整度。草案对 NAT 分类、ICE restart 约束、OPK 扣发、群组前向/后向保密术语差异的理解是准确的，下文不再复述。

---

## 2. 现行实现（对照基线）

今日房间不是对等密信网络，而是**房主权威的局域网星型**：

| 维度 | 现状 |
|---|---|
| 拓扑 | 房主进程开 `WebSocketServer`（默认端口 18765），客人连房主 |
| 范围 | 邀请码携带 LAN IPv4 + 端口；入向依赖同一二层/三层可达 |
| 应用协议 | `RoomFrame`（JSON 帧，自称 transport-agnostic）：hello / welcome / chat / seat / mod / kernel 投影 |
| 身份 | `userId` 为随机 UUID，无密码学身份 |
| 邀请 | `CDR1.` + 固定 XOR 混淆，注释写明「不是军用加密，只是局域网便利令牌」 |
| 可靠性 | 客人断线最多重连 3 次、每次等握手约 30s；无跨通道 ACK / 水位线差量 |
| 权威 | Agent、文件系统、CPA、hostApi 2 的 `room.chat.in`、玩法 reduce 均只在房主进程；客人不执行 kernel |
| 生命周期 | 房主进程重启后房间不再「开着」 |

产品要解决的是：2～6 人围观或共用**一台机器上的 Agent**。不是建设无账号、抗审查、全互联的即时通讯网。

---

## 3. 总体结论

草案的核心思想有三句是对的：

1. 消息层只认会话，不认某条 TCP/UDP 连接。
2. 直连竞速，失败走中继，离线再走异步兜底。
3. 身份与传输分离；密码学走 X3DH / 双棘轮 / MLS 等已验证标准，不自研群密钥。

把这三句做成「Signal + WebRTC + QUIC + MLS + 抗审查信使」的并集，则与本项目目标错位。工程表面积约为现行房间协议的数十倍，且与「房主是特权计算节点」冲突。

更准确的一句话：

> 身份可以去中心，可达性必须机会主义，机密性对中继端到端。房主是会话端点，不是中间方。

草案结尾「从密钥到字节，没有任何一环需要信任第三方」不能作为设计约束。STUN / TURN、MQTT、GitHub / Gitee、证书 CA、Cloudflare 额度、预钥信箱都是基础设施依赖。第三方不能解密，但可以不可用、审查元数据、扣预钥、封账号、丢通知、拒绝中继。

## 4. 方案可取之处（建议保留）

| 点 | 理由 |
|---|---|
| 消息与通道解耦 | 可靠性应挂在 `msg_id` / 水位线上，不能绑死五元组 |
| 直连 → 中继 → 异步 的阶梯 | 消费级 NAT 下这是唯一现实的可达顺序 |
| 国内场景优先 IPv6 | 比「UDP 打洞万能」更贴近 CGNAT 现状 |
| 密码学用标准件 | 1v1 用 X3DH + 双棘轮，小组用 Sender Keys，中组用 MLS；禁止自研群密钥 |
| L0 / L1 交给 ICE 统一 | 比自研六套打洞状态机可交付 |
| TOFU + 安全码，禁止静默换钥 | 去中心身份唯一站得住的信任根 |
| 文档自列的观测、版本协商、预钥治理 | 这些是 Day-1，不是 v2 |

现行 `RoomFrame` 已宣称与传输无关。传输升级应垫在帧下面，用信封替换应用协议是错误方向。

## 5. 主要问题

问题按必须先回应 / 应当修正 / 建议删减 三级。未回应「必须先回应」前，不建议按 v1.2 整包立项。

### 5.1 必须先回应

#### P0-1 信任模型写过了，会带偏后续选型

「不信任任何第三方」与正文中的 TURN、MQTT、Git、预钥信箱互相矛盾。不改这句话，后续会持续出现「再加一条不信任的通道」式自我加戏。

建议改成明确威胁模型，至少区分：

- 被动窃听
- 主动中间人
- 平台拒绝服务
- 元数据观察
- 设备丢失 / 被盗

并单独声明：**房主必须看见聊天明文**（Agent、hook、权限流依赖明文）。端到端防的是中继与仓库，不是房主。

#### P0-2 对等密信网套在了房主权威协作房间上

今日房间是不对称的：房主持有 Agent、文件系统、Mod 执行权；客人是观察者与输入者。权威状态是房主快照，不是成员各自的信封日志。

若「任何中间方只见密文」把房主也当成中间方，Agent 与 `room.chat.in` 立刻没有明文。正确模型是：房主是特权成员（端点），TURN / 对象存储才是中间方。

一旦承认房主特权，下列设计对本项目没有对象：

- 成员全互联 mesh
- 按在线时长 × 带宽选举超级节点
- 用 MLS epoch 替代房主踢人 / 审批 / 权限弹窗

能转发的节点必须有入向。概率上那就是今天的房主，或一台部署的中继，而不是选出来的普通成员。

#### P0-3 身份层与 X3DH 绑定对象矛盾

草案 §2.1 将密钥分成身份钥 / 设备钥 / 会话钥，分层正确。  
§2.2 却用**长期身份钥 IK** 做 X3DH。响应方计算 `DH(EK_A, IK_B)` 必须持有 IK_B 私钥。于是只剩两条路：

| 选法 | 后果 |
|---|---|
| 所有设备共享身份私钥 | 丢一台设备即身份被盗，设备吊销失去意义 |
| 每台设备各自做 X3DH | 文档里的 IK 实际是设备钥，身份钥只负责签发与吊销 |

§3.3「按每个接收设备分别加密一份」走的是后者，§2.2 写成了前者。

多设备必须钉死：

- X3DH 的 IK 是**设备身份**
- 长期身份钥只做签发 / 吊销，不参与 DH
- 历史备份密钥由身份钥经 HKDF 分域派生，禁止与签名、握手复用同一原始密钥

#### P0-4 「一条消息 UDP 发一半、经 Dead Drop 续传」不能写进承诺

双棘轮是整消息原语。跨通道续传只有两种做法，都不成立：

| 做法 | 后果 |
|---|---|
| 先加密再切块 | 切块层必须自带可靠流、偏移、跨通道 ACK，等于在棘轮下再造一条 QUIC |
| 每块走一步棘轮 | 乱序 / 丢块会打爆 skipped-key 窗口；一块永丢则链要跳号，语义变成丢块而非续传 |

Signal / MLS 都不这么做。通道切换应保持草案 §3.2 已有状态机：**未 ACK 的整信封换通道重发**。大文件走独立分片与哈希树，不与聊天信封共用「发一半」。

§4.1 还将「会话」定义为 Connection ID，与 §3.1 的 `conv_id` 撞名。应固定三词：**Conversation / Connection / Path**，不要都叫会话。

### 5.2 应当修正

#### P1-1 六级传输是六套实现，不是一张选路表

L0.1～L0.4 + TURN + Dead Drop 作为选路菜单成立；作为自研清单不可交付。

- QUIC CID 迁移、ICE restart、TCP 同时打开、TLS-443 伪装的迁移语义完全不同
- 草案已承认 TCP / TLS「重建」、Dead Drop「无连接」——「CID 不变、应用无感」只对选定的那一个实时栈成立
- L0.3 TCP 打洞：主流 WebRTC 支持差，国内运营商 TCP 规范化常见，60%–70% 成功率偏乐观，投入产出比最差
- L0.4 的前提是「一侧 443 可被到达」，与自建中继同级，却多了假站、uTLS 与合规话术
- ICE restart 必须走控制面往返，对端离线无法 restart，不能与「应用无感迁移」同时对外承诺
- make-before-break 中断 &lt; 1s 对 QUIC 迁移勉强，对 ICE restart 经常做不到

v1 只应实现一个实时栈：**WebRTC DataChannel（ICE + DTLS + SCTP）+ TURN**。IPv6 作为 host 候选，UDP 打洞作为 srflx，TURN 作为 relay。L0.3 / L0.4 从 v1 删除。

#### P1-2 Dead Drop 不宜承担生产邮箱的四项职责

GitHub / Gitee + 公共 MQTT 当作「总是可达」的 L2，可用性会先于密码学崩溃：

- 把代码托管 / 公共 broker 当消息后端，封号是预期事件
- `git push` 延迟是秒到十秒级，再加限流，不是会话层能抹平的
- 「等全部接收设备 ACK 或 TTL 才删」：一个长期离线设备即可让单会话仓库无限上涨；多设备 × 群成员是乘法
- 公共 MQTT「随机 topic」：topic 若从身份派生则可被监视；若高熵则要先交换，引导问题未解决；知道 topic 就能灌垃圾
- GitHub 与 Cloudflare TURN 在国内都不是「几乎总是」。中国用户的中继必须是国内可达的自建或云中继
- 预钥信箱复用 Git + MQTT，等于没有 Authentication Service，只是一个可被扣预钥的网盘

L2 可以做离线兜底，不能同时承担：多设备同步、群播、预钥目录、控制面。ACK 扇出应改为：投递方（建议仍是房主或专用投递服务）记水位，TTL 硬删；离线设备回来走差量，不保证对象存储里留着每条历史。

#### P1-3 中组 / 大组缺协议角色，且本项目用不上

- 小组 mesh（≤ 5 人）+ Sender Keys：与产品规模匹配，可作为远期选项
- 中组 MLS：RFC 9750 需要 Authentication Service 与 Delivery Service。Commit 载荷 O(log n)，分发仍是 O(n)。用高延迟 Dead Drop 当 DS，Welcome / Commit 时序不可用
- 「无需专用服务器的超级节点」忽略入向约束
- 大组对称群钥并放弃逐人前向保密，对广播可以；与「平台不可信」同时成立时，任何拿过旧钥且能读仓库的人都能看轮换前的历史

本项目 5 人以上也不应上 MLS。继续星型：客人只连房主，房主经 TURN 暴露入向。

#### P1-4 信封替代不了房间状态机

`Envelope` 能搬文本与文件元数据，搬不动现行房间：

- Agent 流式 token、工具卡、权限问答
- `state.snapshot` / `mod.patch` / `mod.priv` / kernel 投影
- 两个客人同时 `seat.takeover` 的冲突（今日靠房主单队列）

Lamport 只能给 UI 一个全序，检测不了并发。草案已写「按发送设备的水位线向量」——**同步应以水位线 + 房主快照为准**，Lamport 只用于展示排序。

TTL 是墙钟，Lamport 是逻辑钟。一面说不依赖时钟同步，一面用 TTL 做死信，必须写明时钟源与允许偏差（例如 10 分钟），否则会死信误杀。

载荷若已是 AEAD，外层再写一个含糊的 `mac` 必须标明覆盖范围，否则是假完整性。明文 `type` 会泄漏业务形态，需在威胁模型里显式接受或收入 AD。

音视频不应以 `type: media-frame` 进入同一条邮箱。媒体需要独立的抖动缓冲、FEC 与拥塞控制，应走独立媒体面（WebRTC），否则会话层会被实时帧撑爆。

### 5.3 建议删减或降级

| 项 | 建议 |
|---|---|
| L0.3 TCP 打洞 | v1 不做 |
| L0.4 TLS-443 伪装 | v1 不做；合规与实现成本都高于自建中继 |
| Git / Gist 作为消息仓库 | 不当控制面，不当预钥目录，不当多设备邮箱 |
| 公共 MQTT 作为唯一通知面 | 可作实验，不能作生产承诺 |
| MLS + SFU + 超级节点选举 | 本项目近期不做 |
| 助记词备份身份钥 | 与设备吊销模型冲突，v1 不做 |
| 多路径聚合（MPTCP 思想） | 在单一实时栈稳定之前不做 |
| 连接迁移 &lt; 1s 的对外承诺 | 改为「同栈迁移尽力；跨栈整信封重传」 |

草案 §13 的「待完善」中，观测埋点与协议版本协商应升为 v1 必做，否则选路参数无法调，新旧客户端无法共存。

## 6. 分层可行性（对本项目）

| 切片 | 可行性 | 说明 |
|---|---|---|
| 现有 `RoomFrame` 下替换传输 | 高 | 应用协议已与传输解耦 |
| 邀请码改为真实密钥派生，停止 XOR | 高 | 补上今日最大的安全缺口 |
| 房主经 ICE + TURN 对外可达，客人仍连房主 | 高，且对准用户痛点 | 真缺口是跨网，不是 mesh |
| 单连接上的 ACK / 去重 / 水位线重连 | 中高 | 可替换「重连 3 次再放弃」 |
| TOFU 设备身份，邀请码携带指纹 | 中 | 不必先上完整 X3DH |
| 完整 X3DH + 双棘轮 + 多设备证书链 | 中，收益滞后 | 房主必须见明文，E2E 防的是中继 |
| MLS + SFU + 超级节点 | 低 | 规模与权威模型都不需要 |
| L0.3 / L0.4 + Git 邮箱全家桶 | 低 | 运维、合规、实现量都超标 |
| 草案描述的完整栈 | **当前不应整包立项** | 量级是独立 IM，不是房间增强 |

## 7. 建议的收敛范围（房间传输 v2）

目标改写为一句，再开规格：

> 房主仍是权威计算节点；传输让公网客人连得上、断线能补洞；中继只见 TLS / DTLS 密文。

### 7.1 做

1. **保留** 应用层 `RoomFrame`（hello / welcome / chat / seat / mod / kernel）。信封若存在，只当传输 PDU，不替换应用协议。
2. **身份 v1：** 每端一对设备密钥；邀请码携带指纹 + 用口令真实 KDF（取代 `CDR1` XOR）；TOFU，指纹变化告警。不做助记词，不做完整多设备吊销网。
3. **传输 v1：** 只做 WebRTC DataChannel + 一台国内可达的 TURN。信令可先继续「邀请码内的候选」或一个最小 rendezvous。不上 MQTT + Git。
4. **会话 v1：** `msg_id` 去重、累积 ACK、按设备水位线差量、重连拉房主快照。整信封重传。禁止跨通道半包续传。
5. **观测 v1：** 建连成功率、路径占比（直连 / TURN）、重连补洞时长。先有数据再调超时与竞速窗口。
6. **版本号：** 传输与应用协议都带版本；旧端遇未知帧类型须可忽略或明确失败，禁止静默损坏房间状态。

### 7.2 明确不做

- TCP 打洞、443 伪装
- Git 死信箱作为邮箱 / 预钥信箱 / 控制面
- MLS、mesh、超级节点选举
- 媒体帧进入聊天信封
- 双棘轮跨通道半包迁徙
- 用对等群密钥替代房主踢人与审批

### 7.3 从草案里真正该吸收的

- 通道可替换（传输可换，房间帧不变）
- 直连与中继分层（ICE 候选，而不是六套自研栈）
- 身份与传输分离（邀请绑定设备指纹，而不是完整 X3DH 全家桶）

---

## 8. 若目标改为「独立的去中心 IM」

与本仓库解绑后，v1.2 可作为 north-star，但立项前仍须先改四件事：

1. 删除「不信任任何第三方」，改为第 5.1 节的威胁模型。
2. 钉死多设备：X3DH 绑定设备钥；写清联系人离线时撤销声明如何送达。
3. 选定唯一实时传输栈，迁移语义只为该栈编写。
4. 为 MLS 显式设计 AS / DS；Dead Drop 降级为离线附件通道，不当 Delivery Service。

在上述四条落地前，完整栈不具备可评审的实现计划。

## 9. 给下一轮审议的问题（请草案作者书面回应）

请按序号回复「接受 / 部分接受 / 不接受 + 理由」，不要只改措辞：

1. 本协议服务的是「房主权威的 Agent 协作房间」，还是「对等密信 IM」？二者不可两头占。
2. 是否同意：房主是端点，必须见明文；E2E 只约束中继与存储？
3. X3DH 的 IK 是身份钥还是设备钥？多设备私钥如何存放、如何吊销？
4. 是否删除「跨通道半包续传」，改为整信封重传？
5. v1 是否只保留 WebRTC DataChannel + TURN，删除 L0.3 / L0.4？
6. Dead Drop 是否降级为可选离线附件，不再承担预钥、控制面、多设备邮箱？
7. 群组是否继续以房主星型为准，MLS / mesh / 超级节点移出本项目范围？
8. `RoomFrame` 是否保持为应用协议？信封是否仅作传输 PDU？
9. TTL 的时钟源与允许偏差是什么？
10. 国内 TURN 的部署主体与预算口径是什么（免费 Cloudflare 额度不能作为产品策略）？

## 10. 结语

v1.2 作为通信自学提纲与分层参考，质量高于常见「上个 WebRTC 就行」的草稿。主病不是某一条 RFC 选错，而是：
