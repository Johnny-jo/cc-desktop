## §1 修订条款（改变原结论，共三条）

### 修订 1：加密边界上移为应用层每信道 AEAD，不再绑定 DTLS

**原条款**：评审回应 Q7 认定「群加密退化为每条客人↔房主 1v1 信道的 DTLS」。

**问题**：DTLS 是 WebRTC DataChannel 传输栈的属性，不是房间协议的属性。绑定后果有三：

1. 局域网 WS 传输上没有 DTLS，同一协议在 LAN 与公网出现两种安全强度；
2. CF Tunnel 路径上 TLS 在 Cloudflare 边缘终止一次，DTLS 不存在，CF 技术上可见明文；
3. 每新增一种传输（WSS / Tunnel / QUIC），都要重新回答「这条路的加密在哪」，与评审 §7.3「通道可替换」自相矛盾——加密钉死在某条通道的传输层，恰恰是没有贯彻通道可替换。

**修订为**：

- 加密层设在 `RoomFrame` 之下、传输之上，作为**应用层每信道加密**：
  - 每端一对设备密钥（X25519），首次连接握手派生会话密钥；
  - 每个 `RoomFrame` 经 AEAD（ChaCha20-Poly1305 或 AES-256-GCM）封装为传输信封；
  - 邀请码携带房主设备指纹，TOFU 校验，指纹变化告警（沿用评审 §7.1 第 2 条）。
- 传输层自带的 TLS/DTLS 降级为**纵深防御**：有最好，没有不影响机密性。
- 机密性边界表述统一改为：**「中继、隧道运营商、存储方只见密文；房主是端点，见明文」**——对 TURN 与 CF Tunnel 一视同仁。

**由此获得**：

- 所有传输（LAN WS / 公网 WSS / CF Tunnel / 未来 WebRTC DC）共享同一安全强度，传输彻底成为可替换哑管道；
- 走 CF Tunnel 时「不暴露账号 + 不暴露内容」同时成立：账号持有者（作者）也只是带宽管道；
- 踢人语义清晰化：踢人 = 废弃该信道的会话密钥 + 断连；重新入房 = 新握手 + 新会话密钥，房主持拒绝权（见修订 3-③）。

### 修订 2：WebRTC / ICE / TURN 整体推迟到 v2，v1 传输三件套

**原条款**：评审 Q5 / P1-1 拍板「v1 唯一实时栈 = WebRTC DataChannel + TURN」；回应接受，并将 Q10（国内 TURN 预算）列为立项前置条件。

**问题**：

1. **信令通道未定义**。ICE 需要持续的信令通道交换 SDP 与候选、支持 ICE restart。两份文件均未指定。且存在循环：若客人能直连房主 TCP 完成信令，说明客人本来就能直连房主——那直接在这条 TCP 上跑 WSS 传 `RoomFrame` 即可，DataChannel 是多余的；若客人不能直连房主，则信令本身就需要一条可达通道，问题转移而非解决。
2. **WebRTC 的收益对象为房主侧无入向的场景**。星型拓扑的前提是「房主尽量公网可达」（回应 §3.4 已写明）。客人是被连方，打洞对客人侧几乎无收益。
3. **实现风险未评估**。房主栈在 Electron 主进程（Node），Node 无原生 WebRTC：`node-datachannel`（libdatachannel 绑定）或借 Electron 隐藏 renderer 用 Chromium WebRTC（需 IPC 桥接）。这是 S1 最大实现风险，两份文件均未提及。
4. **Q10 成为立项阻塞**。为「房主无入向」这一边缘场景，让整个 v2 规格等一笔 TURN 预算拍板，投入产出倒挂。

**修订为**：

- **v1 传输三件套**：
  | 传输 | 适用场景 | 加密 |
  |---|---|---|
  | LAN WS（现有） | 局域网 | 应用层 AEAD（修订 1） |
  | 公网 WSS 直连 | 房主有公网入向（IPv6 / 端口转发） | 应用层 AEAD + TLS 纵深 |
  | CF Tunnel（wss:// 隧道域名） | 房主无公网入向 | 应用层 AEAD（CF 只见密文） |
- **WebRTC DataChannel + ICE + TURN + STUN 整体移入 v2**，触发条件写明：出现相当数量「既无公网入向、又不愿使用隧道」的房主时立项。届时须先补写：信令通道定义、候选交换路径、ICE restart 信令来源、Node 侧实现选型 spike 结论、STUN 部署主体（国内可达，与 Q10 同级决策）。
- **Q10 解除立项阻塞**，不再是「房间传输 v2」前置条件。

### 修订 3：CF Tunnel 定位与域名资产的使用方式

**新增条款**（两份文件均未覆盖作者持有的域名 + CF 账号）：

- CF Tunnel 作为**作者提供的便捷入口 / 小圈子默认项**，使用 named tunnel 挂作者自有域名（如 `room.<域名>`）；`cloudflared` 随软件内置，房主「创建公网房」一键完成。
- **不暴露账号**：房主与客人只见域名；配合修订 1 的应用层 AEAD，账号持有者亦不可见内容。
- **必须写明的定位边界**：
  - 作者账号是单点：隧道不可用则公网房不可用，局域网房不受影响；
  - CF 免费 Tunnel 服务条款偏向个人自用，作为小圈子入口可接受，**不作为面向全体分发用户的公共基础设施承诺**；
  - 协议与代码不依赖该隧道存在：隧道只是 transport 的一种实现，移除不影响协议正确性。
- 房主自建隧道（自己的 CF 账号 + 域名）作为进阶选项支持，邀请码兼容任意 wss:// 地址。

## §2 补写条款（原文件缺失，共四节）

### 补写 1：密码认证协议（取代「口令真实 KDF」的含糊表述）

现状 `CDR1.` 邀请码将房间密码**明文嵌入**码内，泄露即入房。仅把 XOR 换成 KDF 不堵此洞。规定：

- **密码不再出现在邀请码中**。邀请码仅携带：地址（host:port / wss:// 域名）、房主设备指纹、房间名、mod 校验和。
- 握手时以密码做 **PAKE（首选 CPace）** 或最低限度 HMAC 挑战-响应：客户端证明持有密码而不传输密码或其可离线爆破的等价物。
- 密码错误 = 握手失败，与网络错误可区分但**不泄露密码正确性以外的信息**（如成员列表、房间状态）。

### 补写 2：入场审批与设备身份

TOFU 引入后须写明入场控制，否则邀请码泄露 = 永久准入：

- 新设备首次入房：房主侧显示设备指纹 + 名称，**默认需房主审批**；沿用现有 `autoApprove` 开关语义，开启时自动放行但仍记录指纹。
- 设备指纹变化：向房主与本人告警，需重新审批。
- 被踢设备：指纹入房间级黑名单，持旧邀请码重连将被拒绝（呼应修订 1 的密钥轮换语义）。

### 补写 3：公网开放后的滥用与资源防护

局域网假设失效后，攻击面质变，v1 必做：

- 帧大小上限（沿用 `MOD_BUNDLE_MAX_BYTES` 思路，按帧类型分别设限）；
- 每连接速率限制与单客人维度令牌桶（回应 §3.4 只提了房主侧重连风暴，未提单客人维度）；
- 握手超时与半开连接清理；
- 伪造 / 乱序 `roomId`、`seq`、未知帧类型的处理：按版本协商规则忽略或明确失败（沿用回应 §3.5），并计入速率限制；
- 未通过密码认证前不分配任何房间资源（成员席位、mod 状态、会话对象）。

### 补写 4：旧 WS 栈迁移路径

- 应用层 AEAD 对 LAN 与公网**同一代码路径生效**，不维护两套加密逻辑；
- LAN 模式允许房主在创建房间时选择「跳过加密握手」（便利性选项，默认开启加密），该选择写入 `RoomSnapshot` 对全体成员可见，禁止静默降级；
- `CDR1.` 邀请码格式废弃，新格式带版本前缀（如 `CDR2.`），旧码在 v1 内保留只读解码并提示「该邀请码由旧版本生成，安全性不足，请让房主重新生成」。

## §4 修订后的 S1（房间传输 v2）范围一句话

> 房主仍是权威计算节点；`RoomFrame` 之下垫应用层 AEAD 信道与设备身份（TOFU）；传输三件套（LAN WS / 公网 WSS / CF Tunnel）让公网客人连得上；中继与隧道运营商只见密文；密码不进邀请码、认证用 PAKE；观测与版本号 Day-1 必做。

**立项前置条件**：无（原 Q10 阻塞已解除）。WebRTC/TURN/STUN 相关问题随 v2 立项时重新审议。
