| 项 | 内容 |
|---|---|
| 回应对象 | 《CC Desktop 群聊通信架构评审意见》§9 十问 |
| 参照草案 | 《通信协议框架梳理》v1.2 |
| 新增输入 | **群聊人数上限定为 100 人以下，不考虑 100 人以上** |
| 日期 | 2026-08-19 |
| 结论 | **十问中九问接受（一问答「待产品决策」）。在 ≤100 人 + 房主权威两个前提叠加下，草案 §5 群组三层分层整体删除，统一为「客人只连房主、加密到房主为止、踢人即断信道」的单一星型；MLS / Sender Keys / mesh / SFU 全部移出本项目。** |

## 1. 规模上限声明的影响

草案 §5 按规模分三档：≤5 人 mesh + Sender Keys，5–50 人 SFU + MLS，>50 人发布订阅 + 对称群钥。人数上限钉死在 100 之后，这套分层失去存在理由，且带来一个具体危害：

- **档界 50 落在目标区间正中**。群从 49 人涨到 51 人时，拓扑与群密钥协议要整体切换（SFU+MLS → 发布订阅+对称群钥）。「随规模换协议」是工程上最糟糕的形态，等于在常用规模段埋了一个重写点。
- **≤100 是一套拓扑可以通吃的规模**。MLS 的 Commit 分发 O(n) 只有 100 条消息；就算用 Sender Keys，一条消息加密 100 份也是毫秒级。MLS 的 O(log n) 优势在 10³–10⁵ 人才兑现，100 人规模下是纯负债（还要额外养 AS/DS 两个服务）。

**决策：2–100 人统一一种拓扑——房主星型。草案 §5 整节删除。**

## 2. 对评审意见 §9 十问的书面回应

**Q1 本协议服务的是「房主权威的 Agent 协作房间」，还是「对等密信 IM」？**

接受。服务房主权威的 Agent 协作房间。不对等、不做通用 IM。对等密信网的全部设计（mesh、超级节点选举、用群密钥替代踢人审批）移出本项目。

**Q2 是否同意：房主是端点，必须见明文；E2E 只约束中继与存储？**

接受。Agent 流、`room.chat.in`、权限问答都依赖房主持有明文。E2E 的保护对象是 TURN、对象存储、信令通道等中间方，不是房主。威胁模型按评审 §5.1 的 P0-1 重写，区分被动窃听 / 主动中间人 / 平台拒绝服务 / 元数据观察 / 设备丢失，并删除「不信任任何第三方」的表述。

**Q3 X3DH 的 IK 是身份钥还是设备钥？多设备私钥如何存放、如何吊销？**

部分接受。接受「X3DH 绑定设备身份钥，长期身份钥只做签发/吊销、不参与 DH」的钉法；历史备份密钥由身份钥经 HKDF 分域派生，不与签名/握手复用。但 v1 不上完整 X3DH：按评审 §7.1 只做每端一对设备密钥 + 邀请码携带指纹 + TOFU。完整 X3DH + 多设备证书链留作 v2，届时以本问答的钉法为准。

**Q4 是否删除「跨通道半包续传」，改为整信封重传？**

接受。棘轮是整消息原语，半包跨通道续传两种做法都不成立（评审 P0-4 已论证）。通道切换语义为：未 ACK 的整信封回到队列换通道重发；大文件走独立分片 + 哈希树，不与聊天信封共用。术语固定为三词：Conversation（消息会话）/ Connection（逻辑连接，CID）/ Path（五元组），禁止混用「会话」。

**Q5 v1 是否只保留 WebRTC DataChannel + TURN，删除 L0.3 / L0.4？**

接受。v1 唯一实时栈 = WebRTC DataChannel（ICE + DTLS + SCTP）+ 一台国内可达的 TURN。IPv6 作为 host 候选、UDP 打洞作为 srflx、TURN 作为 relay，全部纳入 ICE 统一选路，不自研打洞状态机。L0.3 TCP 打洞、L0.4 TLS-443 伪装删除。连接迁移的对外承诺改为「同栈迁移尽力；跨栈整信封重传」，不承诺 <1s。

**Q6 Dead Drop 是否降级为可选离线附件，不再承担预钥、控制面、多设备邮箱？**

接受，且比评审更进一步：v1 不做 Dead Drop。离线语义定为「离线即错过，重连拉房主快照 + 最近 N 条消息」（见 §3.3）。Git/Gist 仓库与公共 MQTT 不作为消息后端、预钥目录、控制面或多设备邮箱；若未来确需离线附件，以独立可选功能单独立项。

**Q7 群组是否继续以房主星型为准，MLS / mesh / 超级节点移出本项目范围？**

接受，并用规模上限加强论证：

- 客人永不互连，mesh 的唯一价值（去单点、低延迟）对本产品无意义，还多付 N(N-1)/2 条打洞通道的失败率；
- 房主就是唯一转发点，且是房间里唯一大概率有入向能力的节点，SFU 与超级节点选举没有对象；
- 房主是端点且必须见明文（Q2），「群加密」退化为「每条客人↔房主 1v1 信道各自加密（DTLS）」，群消息 = 房主解密后在其余 n-1 条信道上加密转发。**群密钥问题整体消失，MLS 与 Sender Keys 都不需要**；
- 群组的前向/后向保密（踢人后看不到新消息、新成员看不到历史）退化为「断开该客人的信道 + 该信道密钥轮换」，O(1) 操作，天然成立。

**Q8 `RoomFrame` 是否保持为应用协议？信封是否仅作传输 PDU？**

接受。`RoomFrame`（hello / welcome / chat / seat / mod / kernel 投影）保持为应用协议不动；传输升级垫在帧下面。信封若存在只当传输 PDU。Lamport 仅用于展示排序，同步以水位线 + 房主快照为准。媒体帧不进聊天信封，音视频走独立媒体面（未来如需）。

**Q9 TTL 的时钟源与允许偏差是什么？**

接受问题本身，回答：v1 砍掉信封级 TTL——离线语义改为「重连拉快照」（Q6），聊天消息不存在「死信」。TTL 仅在未来的离线附件通道中引入，届时规定：以发送方墙钟为准，允许偏差 ±10 分钟，超差按未送达处理而不误杀。

**Q10 国内 TURN 的部署主体与预算口径是什么？**

待产品决策，此处只列选项与约束：

| 选项 | 说明 |
|---|---|
| 自建 coturn（国内云主机） | 可控、成本固定；需要运维与域名证书 |
| 云中继服务（国内厂商） | 免运维，按量付费；需评估凭据分发与合规 |
| Cloudflare TURN 免费额度 | 评审已指出不能作为产品策略，仅可作开发期实验 |

约束不变：TURN 只见 DTLS 密文，只兜底打不通的客人；房主应尽量公网可达（IPv6 / 端口映射），避免 100 人流量全压 TURN。**此项在「房间传输 v2」立项前必须拍板。**

## 3. ≤100 人统一星型下的基础问题清单

以下是与规模决策绑定、必须在 v2 规格中写明的基础问题。

### 3.1 拓扑与权威

- 单一拓扑：客人都连房主，客人之间无任何通道。权威状态 = 房主快照，与今日实现一致。
- 删除：mesh、SFU、超级节点选举、MLS、Sender Keys、大组发布订阅。

### 3.2 加密边界与威胁模型

- 加密到房主为止：每条客人↔房主信道独立 DTLS；中继/存储只见密文。
- 必须明示的代价：**房主机器被攻破 = 全群明文**。这是产品形态的内禀属性，写入威胁模型，不当作缺陷修补。
- 群成员变动保密性 = 断信道 + 信道密钥轮换（O(1)），不引入群密钥协议。

### 3.3 离线语义

- 离线即错过：不承诺离线消息留存。重连后拉房主快照 + 最近 N 条消息。
- 由此连带删除：Dead Drop 邮箱协议、manifest、「等全部设备 ACK 才删」的清理逻辑。100 人 × 多设备的 ACK 乘法问题不存在了。

### 3.4 真正的瓶颈在房主，不在协议

- **上行扇出**：每条消息广播 n-1 份。文本无所谓，Agent 流式 token 是持续流——按 ~10KB/s 流 × 99 客人 ≈ 1MB/s 上行。需要写合并与背压。
- **快照成本**：状态快照必须差量化；一次全量快照广播 = 快照大小 × 99。
- **重连风暴**：网络抖动后几十人同时重连拉快照，需令牌桶 + 快照缓存。
- **入向可达**：房主尽量公网可达（IPv6 / 端口映射）；TURN 只兜底。若房主无入向，100 人全部流量过 TURN，带宽成本集中（与 Q10 联动）。

### 3.5 Day-1 项（从草案 §13 升级为 v1 必做）

- 观测埋点：建连成功率、路径占比（直连/TURN）、重连补洞时长。
- 协议版本协商：传输与应用协议都带版本；旧端遇未知帧类型可忽略或明确失败，禁止静默损坏房间状态。

## 4. 拓展路线与成本

| 阶段 | 规模 | 要做什么 | 协议变化 | 主要成本 |
|---|---|---|---|---|
| S0 现状 | 2–6 LAN | — | — | — |
| S1 房间传输 v2 | 2–30 | 设备密钥 + 邀请码真 KDF（废 `CDR1` XOR）+ TOFU；WebRTC DataChannel + 一台国内 TURN；msg_id 去重 / 累积 ACK / 按设备水位线差量 / 重连拉快照；观测与版本号 | 传输层垫在 `RoomFrame` 下，应用协议不动 | 一次性开发；TURN 近零流量 |
| S2 稳定 100 | 30–100 | 房主扇出优化（写合并、快照差量、旁观者只读流）；重连风暴治理；TURN 带宽规划或房主导流 | **不变** | 房主上行带宽 + TURN 流量费，纯运维成本 |
| S3a 超 100 围观（若需要） | 100–1000+ | 加只读扇出中继：房主→中继→观众，中继只见 DTLS 密文 | **不变**，权威与密码学不动 | 基础设施按量付费 |
| S3b 对等 E2E 大群（若转向） | — | MLS + Authentication/Delivery Service，放弃房主明文 | 整体换群密钥层，等于另一个产品 | 与本项目定位冲突，不建议 |

关键性质：

- **S1→S2→S3a 是平滑斜坡**：不加密码学、不换拓扑，花的只是带宽钱。这是「≤100 统一星型」买到的最值钱的东西——没有 50 人处的协议悬崖。
- **S3b 是唯一需要 MLS 的场景**，但它要求转发者不可信，与房主权威根本矛盾。真走到那步是另立产品，不是本项目的「拓展」。

## 5. 下一步

下一轮只审议「房间传输 v2」规格，范围以评审意见 §7 为准，加上本文档的三处收紧：

1. 群组不再分档，2–100 人统一房主星型（草案 §5 删除）；
2. 群密钥层整体取消，加密边界 = 每条 1v1 信道的 DTLS；
3. 离线语义 = 重连拉快照，Dead Drop 全系（邮箱/预钥/控制面/群播）移出 v1。
